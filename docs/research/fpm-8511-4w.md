# PHP 8.5.11 FPM 128M 4-worker pure-HTTP chain

Lab-only research note, curated from the main research log (`docs/111`).
Authorized lab targets only; see `ACCEPTABLE_USE.md` and `SECURITY.md`.
The engine chain and constants are identical to the 1-worker 8.5.11 proof
(`docs/research/fpm-8511-http.md`); this note covers the multi-worker
orchestration, the conf.d pitfall and the BG dual-offset fix.

## Result

PHP 8.5.11 FPM, 128M, `pm=static` 4 workers, scheduled with the lab
`_sleep.php` page:

- PoC single round with `P4W_GDB=1`: `ASSERT OK` + `ASSERT4 OK` (202 s;
  `gdb_hits=11` is the expected calibration reading);
- in-run `ROUNDS=3`: **PASS=3/3**, `ASSERT4 OK` x3, measured sampler
  `gdb_hits=0`, **301 s**;
- three independent `ROUNDS=1` runs: **PASS / PASS / PASS**,
  **123 / 110 / 122 s**;
- Lead matrix 3 runs: PASS (98.9 / 121.8 s and a third PASS block; each 1/1,
  `gdb_hits=0`, `ASSERT4=1`);
- proof: `/srv/www/x.php` = 392 B, `GET /x.php?0=id` = `uid=33(www-data)`;
  R2a/R2a(K2) session bytes 47 B / 70 B;
- matrix at registration: **60 = 51 proof + 2 refuse + 6 gap + 1 gate,
  23/60 `oracle=http`**; A/B **87.55 / 85.05** unchanged (lab scheduling).

## Container, image and conf.d pitfall

| Item | Value |
|---|---|
| Image | `p2s-phpfpm-lab:8.5.11` = `sha256:502117d6add8...f9ee918b` |
| Container | `p2s-fpm8511-4w`, host port **19142** (1w lab: `p2s-fpm8511-128`/19113) |
| Pool | `pm=static`, `pm.max_children=4` (`www-4.conf`), `request_terminate_timeout=120s`, `catch_workers_output=yes` |
| Mounts | `www-4.conf` + `php-128m.ini` + a new `zz-r40-lab.ini` conf.d override |
| gdb / exclusivity | `--cap-add SYS_PTRACE` for one-off `P4W_GDB=1` calibration only; the 4w container must be exclusive (sleepers occupy 3/4 workers) |

**conf.d pitfall (must be quoted):** the shared `php-128m.ini` is now
`cleanup=On` (19113 runs an older `cleanup=Off` copy, and the 8.5.11 image
default is On), so mounting only that ini loses the HTTP-grown SP session
(cleanup removes the upload-progress record; `SP != 7,050,470 B`). Fix: mount
a new `zz-r40-lab.ini` with `session.upload_progress.enabled = On` +
`session.upload_progress.cleanup = Off`, and verify in the web context
(`cleanup=Off / enabled=1 / memory_limit=128M`) after every image change or
restart.

## Pinning, ASSERT4 and the BG dual-offset fix

- The `WORKERS=4` pinning is the same as 8.2.34
  (`docs/research/fpm-8234-4w.md`): per round restart -> HTTP grow
  SP = 7,050,470 B -> restart -> 3x concurrent `GET /_sleep.php?t=60`
  (marker = child PID) -> free = 4 - 3 = 1 -> prime
  `GET /_r41prime2.php?mb=114&pad=64` (500/0 B) -> R2a (SR 47/70) -> R3
  (`x.php` 392 B, `uid=33`) -> kill sleepers. `ASSERT4 OK` has the same
  fields as the 8.2.34 4w run.
- **BG offset fix (core of this round):** `BG(unserialize).level` lives at
  **+0x370** on 8.5.11 and **+0x358** on 8.2.34. The old `bg4_scan` tried
  `L358` first and fell back to `L370` only when the value was empty; on
  8.5.11 `+0x358` is a legitimate 0, so it never fell back, `primed_pid`
  stayed `NONE` and `ASSERT4` failed. The runner now parses **both offsets**
  and accepts either `== 1`, while keeping `level1_count == 1` to prevent a
  double-hit false positive (after the fix:
  `PINCHECK primed_pid=11 free_pid=11 level1_count=1`).
- The optional `P4W_GDB=1` check is calibration only (never inside the 3/3
  sampler runs); the wrapper requires `ASSERT4 OK` with no `FAIL`.
- child ids change per restart; judges use marker/free identity, the SR/x.php
  oracles and `health`, never a fixed PID.

## Limitations

- pinning is a lab scheduling precondition (`_sleep.php` + exclusive container
  + `pm=static` 4 + `zz-r40-lab.ini` cleanup=Off + `request_terminate_timeout`
  120 s); re-calibrate marker/free/SR after image/pool/page changes;
- **the shared `php-128m.ini` is `cleanup=On`:** always use the conf.d override
  and verify the web context after an image change;
- `log_errors=Off` in this pool means no fatal text; the OOM is judged from
  prime 500/0 B + SP truncation + calibrated `BG=1` + the SR oracle
  (`fatal=inferred`);
- `P4W_GDB=1` is calibration only; the reported 3/3 runs are gdb-free;
- each round costs ~110-125 s (restart dominated) and 4w is not a new
  vulnerability primitive (same engine chain, lab scheduling).
